# C# в Unity — стиль, ревью и готовность задачи

## Стиль кода

1. Используй `PascalCase` для типов и публичных членов, `_camelCase` для приватных полей и `camelCase` для параметров и локальных переменных.
2. Дай классу одну ответственность. Название вроде `Manager` — повод проверить, ясно ли назначение класса.
3. Делай API настолько узким, насколько позволяют вызовы. Выбирай `private` или `internal`, если внешний доступ из проекта не нужен.
4. Ссылки на компоненты задавай в инспекторе, передавай явно или кешируй при инициализации. В покадровом коде используй уже подготовленные ссылки.
5. Для сериализуемых полей компонентов используй `[SerializeField] private`. Публичные поля оставляй для простых структур данных, если это часть их контракта.
6. Проверяй входы на границах системы. Для ошибочных входов доменная логика использует понятный контракт, например явный результат `Try…` или исключение.
7. Настройки баланса держи в конфиге. Для устойчивых технических значений давай константам имена, объясняющие их роль.
8. Комментариями поясняй причину решения и ограничения. Название и структура кода показывают, что он делает.
9. Если в репозитории есть `.editorconfig`, используй его как общий источник правил форматирования.
10. Имя файла с публичным типом совпадает с именем типа. Обычно один публичный тип на файл.

## Чек-лист ревью

- [ ] Правила и вычисления проверяются отдельно от сцены, если для них достаточно входных данных.
- [ ] Ссылки между `.asmdef` идут в разрешённом направлении, а `Core` обходится без `UnityEngine`.
- [ ] Конфигурация, технические константы и изменяемое игровое состояние имеют явные места хранения.
- [ ] Покадровый код использует подготовленные ссылки и передаёт правила модели, которую можно прогнать отдельно.
- [ ] Публичный API нужен его вызывающим сторонам. Некорректные входные данные обработаны на границах.
- [ ] Новая логика `Core` покрыта EditMode, когда применимо. Для изменений сцены и интерфейса проверена затронутая связка.
- [ ] Форматирование соответствует правилам репозитория, а изменившиеся договорённости отражены в тематических заметках.

## Когда задача готова

Код компилируется, изменённая сцена или сборка запускается, сценарий работает вручную. Применимые тесты проходят локально, замечания ревью исправлены, а документация обновлена для изменившихся правил и зависимостей. Для релизной вехи выполняется отдельный прогон сборки.
