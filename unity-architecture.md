# Unity — архитектура и технологии

Базовая схема для небольших Unity-игр. Она помогает проверять игровые правила без запуска сцены, менять баланс через данные и переносить логику между проектами.

## Разделение на сборки

Храни код игры в `Assets/_Project/`. Заводи `.asmdef` для слоя, когда у него появляется своя ответственность. Таблица показывает допустимые зависимости между сборками проекта.

| Сборка | Ответственность | Может ссылаться на |
|---|---|---|
| `Core` | Игровые правила, формулы, состояние и переходы | Стандартная библиотека C# |
| `Data` | Авторские конфиги и преобразование в значения для `Core` | `Core` |
| `Gameplay` | Unity-адаптеры ввода, времени и сцены | `Core`, `Data` |
| `UI` | Представления, кнопки и отображение состояния | `Core`, `Gameplay` |
| `Infrastructure` | Адаптеры сохранений, звука и внешних сервисов по мере необходимости | `Core` |
| `Bootstrap` | Точка сборки игровых зависимостей на запуске | Используемые сборки проекта |

Для `Core` включи **No Engine References** в Assembly Definition Inspector. Игровая математика живёт в обычных C#-типах. `MonoBehaviour` принимает ввод, передаёт команды модели и отображает результаты. Один `Bootstrap` связывает зависимости при запуске. [Руководство Unity по Assembly Definition](https://docs.unity.com/en-us/engine/6000.6/manual/programming-environment/script-compilation/assembly-definition-files/class-assembly-definition-importer)

```text
Assets/_Project/
  Core/
  Data/
  Gameplay/
  UI/
  Infrastructure/
  Bootstrap/
  Tests/
    EditMode/
    PlayMode/
```

## Данные и фиксированный шаг

- **ScriptableObject** подходит для авторских данных, которые удобно править в инспекторе. Адаптер передаёт модели обычные значения. Текущее состояние попытки хранится отдельно. Для проектов с сохранениями используй отдельный формат сохранения, а валидатор конфигов проверяй в EditMode. [Руководство Unity по ScriptableObject](https://docs.unity.com/en-us/engine/6000.6/manual/scripting/get-started/fundamental-unity-types/class-scriptable-object)
- **Фиксированный шаг** подходит, когда результат зависит от точного порядка движения, таймеров и ввода. Адаптер привязывает команды к шагу, модель выполняет правила в заданном порядке. Запись для воспроизведения содержит конфигурацию или её версию, начальное состояние, номера шагов и команды. Если модель использует случайность, добавь начальное состояние её генератора. Для чисел с плавающей точкой задавай допуск и проверяй повторяемость на целевых платформах.
- **Input System** подходит для нескольких физических привязок одного действия. Например, клавиша и кнопка интерфейса отправляют одну смысловую команду, а правило обработки совпадений остаётся в игре. [Руководство Input System](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.19/manual/QuickStartGuide.html)
- **URP 2D Renderer** подходит, когда спрайты должны реагировать на настраиваемое 2D-освещение. Интерактивную геометрию держи в модели. Если видимая граница света влияет на решение, отрисовывай её по тем же параметрам, что использует модель. [Руководство Unity по 2D-свету в URP](https://docs.unity.com/en-us/engine/6000.6/manual/unity2d/2d-urp/2d-index/2d-light-properties-explained)

## Как записывать новую технологию

Дополни заметку по подходящей теме. Зафиксируй, какую проблему решает инструмент, когда он нужен, от чего зависит и как проверить результат. Для пакета укажи точный ID и версию, которую использовал конкретный проект. Версии и параметры проекта удобнее держать в примере в конце заметки. Статус «записано в манифесте» отражает зависимость проекта, статус «проверено» требует проверки в редакторе или сборке.
