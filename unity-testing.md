# Unity — тестирование и приёмка

Базовый процесс для локальной разработки. EditMode покрывает правила и данные, PlayMode — критичные связки со сценой, ручной прогон — качество игрового опыта и поведение готовой сборки.

## Выбор уровня проверки

| Режим | Что проверять |
|---|---|
| **EditMode** | Формулы и граничные значения, переходы состояний, экономику, правила прогрессии, сериализацию и миграции сохранений, валидность конфигов. |
| **PlayMode** | Связки с `MonoBehaviour`, жизненным циклом сцены, корутинами и физикой Unity. Примеры — игровой сигнал после действия, привязка UI к состоянию, возврат объекта в пул, полный цикл сохранения через реальные адаптеры. |
| **Ручная проверка** | Ощущение управления и темпа, читаемость, громкость и атмосфера. Для сборки также проверяем запуск, совместимость, смену фокуса и производительность в целевой среде. |

Если результат зависит только от данных и правил, проверяй его обычным тестом EditMode. Таймер с заданным шагом можно проверить численно. Ощущение, достаточно ли времени у игрока, оценивается в плейтесте. Держи основную массу тестов в EditMode и добавляй PlayMode на важные стыки, которые требуют реальной сцены. [Руководство Unity по EditMode и PlayMode](https://docs.unity.com/en-us/engine/6000.6/manual/programming-environment/test-framework-introduction/getting-started/edit-mode-vs-play-mode-tests)

## Локальный прогон

Открой **Window → General → Test Runner**. Вкладки **EditMode** и **PlayMode** позволяют запустить отдельный тест или **Run All**. [Руководство Unity по Test Runner](https://docs.unity.com/en-us/engine/6000.6/manual/programming-environment/test-framework-introduction/running-tests/workflow-run-test)

- Перед коммитом в основную ветку запускай EditMode.
- Перед вехой разработки запускай оба набора и вручную проверяй сборку. При активных изменениях сцены добавляй промежуточный прогон PlayMode.
- Для записи результата укажи сборку или коммит, сценарий, ожидаемый и фактический результат. Для браузера укажи версию и разрешение. При сбое сохрани шаги воспроизведения.

| Этап | Что добавлять к обычным проверкам |
|---|---|
| Прототип и вертикальный срез | EditMode на основную механику. Внутренний плейтест прототипа и внешний прогон вертикального среза. |
| Продакшн | Тесты на новую логику и выборочные интеграционные проверки для новых связок. |
| Альфа | Полный прогон тестов. Плейтест на темп, сложность и понимание правил. |
| Бета | Полный прогон тестов и замеры производительности на целевых конфигурациях. |
| Релиз | Финальный набор тестов и ручная проверка именно той сборки, которая пойдёт игрокам. |

## Воспроизводимые сценарии

Пиши сценарий как начальное состояние, команды в заданном порядке и ожидаемый результат. Для модели с фиксированным шагом указывай номера шагов и сравнивай наблюдаемые результаты. Для коротких наборов граничных значений подойдёт NUnit `[TestCase]`. [Документация NUnit по TestCase](https://docs.nunit.org/articles/nunit/writing-tests/attributes/testcase.html)

```csharp
using NUnit.Framework;

public class DamageCalculatorTests
{
    [TestCase(0, false, 0)]
    [TestCase(100, false, 100)]
    [TestCase(100, true, 200)]
    public void Calculate_ReturnsDamage(int baseDamage, bool isCritical, int expected)
    {
        Assert.That(DamageCalculator.Calculate(baseDamage, isCritical), Is.EqualTo(expected));
    }
}
```

Это пример для проекта с `DamageCalculator`. Для сценариев сцены готовь понятное стартовое состояние и очищай созданные объекты после теста. Если проверка требует дождаться события, ожидай наблюдаемое условие с ограничением времени.
